01 / Quick Start

Your first project in under a minute

Folio is designed to feel like an app — not a website. Everything works on a phone, everything is offline-ready, and there's no setup step between you and writing code.

What Folio is

Folio is a code editor that runs entirely in your browser. Nothing to install, no dependencies, no build pipeline to break. Open the site, sign in (or skip that and stay a guest), and start coding.

Every project you create lives in two places at once:

  • On your device, inside your browser's storage — this is what lets Folio work without internet, and what makes saving instantaneous.
  • On the server, when you're signed in — this is what makes sync, deploy, and collaboration possible.

Sign in vs. guest

FeatureGuestSigned in
Create & edit projects✓ Local only✓ Synced
Preview projects✓✓
Deploy to a live URL—✓
Invite collaborators—✓
Analytics—✓
JSON database—✓
Push notifications—✓
Try it without signing up

You can use Folio as a guest forever. When you're ready to keep your work safe across devices, sign in from the profile icon.

Create your first project

  1. Tap New project — a short modal asks for a name.
  2. Pick a template: Blank, Landing, Todo, or Blog.
  3. Tap Create, and you're in. Folio opens index.html automatically.
You don't need to save manually

Folio auto-saves 2 seconds after you stop typing. The Ctrl + S shortcut exists if you want to force it, but you'll rarely need it.

02 / The Editor

Where you write the code

A full-featured code editor built on CodeMirror 6, tuned for touch first and thumb-typing second.

What's included out of the box

Folio's editor isn't a textarea with monospace text. It's a real code editor — with syntax highlighting for HTML, CSS, JavaScript, TypeScript, JSON, Markdown, Python, and more.

Syntax highlighting

Real color for real languages. HTML tags, CSS selectors, JS keywords, JSON keys.

Undo & redo

Unlimited history. No "you can only undo 10 edits" limits.

Find & replace

Full-document search with regex, case-sensitive, and whole-word options.

Auto-format

One tap formats HTML, CSS, JS, JSON, and Markdown with Prettier.

The toolbar

Below the editor sits a persistent toolbar. Everything is one thumb-tap away.

ButtonWhat it does
SaveForce a save right now
Undo / RedoStandard undo/redo
CtrlModifier latch (see below)
FindOpen search panel
FormatFormat current file
MoreReveal the secondary row

The Ctrl latch

Physical keyboards have a Ctrl key. Phones don't. Folio fixes this with the Ctrl latch — tap Ctrl to "arm" the modifier, then tap the next key to fire a shortcut.

  • Tap Ctrl, then Z → undo
  • Tap Ctrl, then S → save
  • Tap Ctrl, then F → find
  • Tap Ctrl, then A → select all
The latch cancels itself

If you tap Ctrl and then don't tap a valid key, the latch clears. Or tap Esc. Either way, it won't get stuck.

Symbols — the ones phones hide

Every phone keyboard hides the symbols code needs most. Folio gives you a 32-symbol sheet one tap away.

{ } < > ; : = == & | $ # / \ ! ?
03 / Files & Folders

Structured like a real project

Folio's file tree behaves like your laptop's — except it fits in your thumb.

The file tree

On the left (or behind the menu button on mobile) sits the Files panel. Tap a folder to expand it, tap a file to open it, drag to scroll.

Creating files with paths

You can create files with paths. Type src/app.js and Folio creates a src folder and puts app.js inside. Nested paths work too: src/components/Button.jsx creates three levels.

Renaming and deleting

Hover (or long-press on mobile) any file or folder to reveal Rename and Delete.

Deletes are permanent

There's no trash bin. If you want a safety net, commit before you delete anything — that way you can restore the file from version history.

Importing files

Tap Import and Folio opens your device's file picker. Text files are imported as-is. Images, PDFs, videos, and audio are stored as data URLs — they work offline and sync with your project.

Filtering

Above the tree is a filter input. Type any substring to filter the tree live. It searches the full path.

04 / Preview

See your project run

Three ways to preview, each designed for a different moment.

Three preview modes

Tap Preview to run your project. Tap the caret next to it to switch modes.

Fullscreen

A dedicated full-screen view with an in-app console at the bottom.

New tab

Opens in your browser's own tab. Best for real browser environment testing.

Mini panel

A floating mini-window in the corner. Best for live updates while you edit.

What happens under the hood

  1. Finds your HTML file — preferring index.html at the root.
  2. Inlines every linked CSS file into a <style> tag.
  3. Inlines every linked JS file into a <script> tag.
  4. Injects a console bridge that forwards console.log output.

The result is a single self-contained HTML document that runs identically to how it would if deployed.

Console output

In fullscreen mode, the bottom pane shows everything your code logs:

app.js
javascript 
console.log('hello');   // appears in the pane
console.warn('careful'); // appears in amber
console.error('oops');   // appears in red

07 / Commits

Version history without git

Folio gives you the safety net of version control without the complexity of branches, remotes, or merge conflicts.

What a commit is

A commit is a snapshot of your entire project at a moment in time. Every file, captured together. Unlike git, Folio's commits are linear — no branches, no merge conflicts, no "detached head."

Making a commit

  1. Tap Commit in the editor toolbar.
  2. A modal opens showing all files changed since your last commit.
  3. Folio auto-generates a message — edit it or accept it.
  4. Tap Commit, and the snapshot is saved.

Comparing commits

Tap Diff on any commit to see what changed. Colour-coded:

  • Green = lines added
  • Red = lines removed
  • Amber = lines changed

Restoring to an old commit

Tap Restore on any commit. Folio rewrites your entire project to that snapshot. Before restoring, it automatically creates a snapshot of your current state — so even restoring is reversible.

Restoring affects the whole project

Files created after that commit are removed. Files deleted after that commit come back.

08 / Notes

A notebook inside every project

Every project has its own notes panel — not one giant text field, but a proper list of individual notes.

Why multiple notes

Real projects have many thoughts: a README draft, a TODO list, a snippet you'll want later, a design decision you need to remember. Each idea gets its own note.

Creating and editing

Open the Notes panel from the editor sidebar. Tap New note. A fullscreen editor opens with a title, body, word counter, and actions. Notes auto-save 800 ms after you stop typing.

Six accent colours

Amber · General Sky · Reference Violet · Ideas Emerald · Done Rose · Warnings Cyan · Snippets
Notes are private by design

When you deploy, notes are excluded from the deployment. Your private notes never end up on your public URL.

Inviting someone

  3. Pick a role.

  • Live site link — shows a "Visit live site" button

10 / Deploy

Your project, on the internet

Deploy any project to a live URL with one tap. No build steps, no configuration, no CI.

What deploy does

  1. Collects every file in your project.
  2. Applies your meta tags to the primary HTML file.
  3. Uploads everything to Folio's servers.
  4. Returns a live URL that serves your project.

Where the URL lives

Every deploy gets a URL on Folio's infrastructure. Your project's slug becomes part of the path.

Live URL format
text 
https://foliostudios.vercel.app/api/host
  ?action=serve
  &pid=YOUR_PROJECT_ID
  &path=index.html

Deploy limits

Each project can be deployed up to 10 times per hour. Deploying requires an account — guests can build and preview but not deploy.

Taking offline

If you want to take a project offline temporarily without deleting it, use Take offline. Files and history stay intact. Redeploy any time.

11 / JSON Database

Read and write JSON from your deployed site

Every project has a private JSON blob attached to it — a key-value store you can read and write from your deployed site.

Not a real database

No queries, no indexes, no per-user records. It's enough for guestbooks, site config, todo lists, and small dynamic content.

Enable public reads

By default, nobody can read the DB. To let visitors read it, go to your project page → Sharing → flip JSON database API to Public.

Reading from your site

read-db.js · public read
javascript 
const res = await fetch(
  'https://foliostudios.vercel.app/api/host' +
  '?action=db/get&pid=YOUR_PID'
);
const { data } = await res.json();
console.log(data);

For private reads, send the project's API key in an x-project-key header:

read-db.js · private read
javascript 
const res = await fetch(
  'https://foliostudios.vercel.app/api/host' +
  '?action=db/get&pid=YOUR_PID',
  { headers: { 'x-project-key': 'fol_...' } }
);

Writing — three modes

Writes always require the API key. Generate one at project page → Sharing → API key.

ModeBody shapeUse when
Path write{ key, value }Editing one field
Merge write{ data, mode: "merge" }Replacing a subtree
Replace write{ data }Full DB replacement
Recommended for edits — only the target path changes.
path-write.js
javascript 
// Set posts/p_abc/heart to 42,
// leaving every other post intact
await fetch(
  'https://foliostudios.vercel.app/api/host' +
  '?action=db/set&pid=YOUR_PID',
  {
    method: 'POST',
    headers: {
      'content-type': 'application/json',
      'x-project-key': 'fol_...'
    },
    body: JSON.stringify({
      pid: 'YOUR_PID',
      key: 'posts/p_abc/heart',
      value: 42
    })
  }
);
Top-level keys you send are replaced — the rest of the DB is untouched.
merge-write.js
javascript 
// Replace config wholesale;
// leave posts and members alone
await fetch(
  'https://foliostudios.vercel.app/api/host' +
  '?action=db/set&pid=YOUR_PID',
  {
    method: 'POST',
    headers: {
      'content-type': 'application/json',
      'x-project-key': 'fol_...'
    },
    body: JSON.stringify({
      pid: 'YOUR_PID',
      data: { config: { theme: 'dark' } },
      mode: 'merge'
    })
  }
);
Wipes the entire DB — only use for resets or imports.
replace-write.js
javascript 
// Wipe the DB and set it fresh
await fetch(
  'https://foliostudios.vercel.app/api/host' +
  '?action=db/set&pid=YOUR_PID',
  {
    method: 'POST',
    headers: {
      'content-type': 'application/json',
      'x-project-key': 'fol_...'
    },
    body: JSON.stringify({
      pid: 'YOUR_PID',
      data: {
        config: { theme: 'dark' },
        posts: {},
        members: {}
      }
    })
  }
);
Merge is NOT a deep merge

If you send { posts: { p_abc: {...} } } with merge mode, the entire posts object becomes { p_abc: {...} } — every other post is dropped. Use a path write to update one post without wiping others.

Which mode should I use?

  • Editing one field (a reaction, a vote, a rename) → path write (key + value)
  • Updating a whole top-level object (config, members, posts) → merge write (data + mode: "merge"), sending the complete subtree
  • Resetting / importing / atomic replace → replace write (data, no mode)

Limits & security

15 MB total per project DB. Writes that push the DB over the limit return 413.

100 writes per hour per project. The response includes rateLimit and space so you can back off gracefully.

Writes are not transactional. If you send a replace write while another client is mid-merge, one wins silently.

If you embed the API key in client-side JavaScript, anyone who opens DevTools can read it and write to your DB.

For anything beyond a toy project, put the key in a small backend and proxy writes through it.

Recipe 2 — Todo list app

A working todo list with add, toggle, and delete. Works entirely client-side.

index.html
html 
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>Todo</title>
  <link rel="stylesheet" href="style.css">
</head>
<body>
  <main class="app">
    <h1>Todo</h1>
    <form id="new-todo">
      <input type="text" id="todo-input" placeholder="Add a task…" required>
      <button type="submit">Add</button>
    </form>
    <ul id="todo-list"></ul>
  </main>
  <script src="app.js"></script>
</body>
</html>
app.js
javascript 
const form = document.getElementById('new-todo');
const input = document.getElementById('todo-input');
const list = document.getElementById('todo-list');

function addTodo(text) {
  const li = document.createElement('li');
  const cb = document.createElement('input');
  cb.type = 'checkbox';
  cb.addEventListener('change', () => {
    li.style.opacity = cb.checked ? '0.5' : '1';
    li.style.textDecoration = cb.checked ? 'line-through' : 'none';
  });
  const span = document.createElement('span');
  span.textContent = text;
  const del = document.createElement('button');
  del.textContent = '×';
  del.className = 'delete';
  del.addEventListener('click', () => li.remove());
  li.appendChild(cb);
  li.appendChild(span);
  li.appendChild(del);
  list.appendChild(li);
}

form.addEventListener('submit', (e) => {
  e.preventDefault();
  const text = input.value.trim();
  if (!text) return;
  addTodo(text);
  input.value = '';
  input.focus();
});

Recipe 4 — Writing one field (path write)

Update a single value without touching anything else in the DB. This is the safest write mode.

update-heart.js
javascript 
// Update a single field in your JSON DB.
// Only the target path changes — siblings untouched.

async function updateHeart(postId, count) {
  const res = await fetch(
    'https://foliostudios.vercel.app/api/host' +
    '?action=db/set&pid=YOUR_PID',
    {
      method: 'POST',
      headers: {
        'content-type': 'application/json',
        'x-project-key': 'fol_YOUR_API_KEY'
      },
      body: JSON.stringify({
        pid: 'YOUR_PID',
        key: 'posts/' + postId + '/heart',
        value: count
      })
    }
  );
  const result = await res.json();
  console.log('Updated:', result);
  return result;
}

Recipe 5 — Storing form submissions

A working contact form that saves each submission to your JSON DB.

contact.js
javascript 
// A working contact form.
// Saves each submission under a unique key.

const form = document.getElementById('contact-form');
const status = document.getElementById('status');

form.addEventListener('submit', async (e) => {
  e.preventDefault();
  const name = document.getElementById('name').value;
  const message = document.getElementById('message').value;
  const id = 'msg_' + Date.now();

  status.textContent = 'Sending…';

  try {
    const res = await fetch(
      'https://foliostudios.vercel.app/api/host' +
      '?action=db/set&pid=YOUR_PID',
      {
        method: 'POST',
        headers: {
          'content-type': 'application/json',
          'x-project-key': 'fol_YOUR_API_KEY'
        },
        body: JSON.stringify({
          pid: 'YOUR_PID',
          key: 'messages/' + id,
          value: { name, message, sentAt: Date.now() }
        })
      }
    );
    if (!res.ok) throw new Error('Failed');
    status.textContent = 'Thanks! We got your message.';
    status.style.color = '#10B981';
    form.reset();
  } catch (err) {
    status.textContent = 'Something went wrong. Try again.';
    status.style.color = '#EF4444';
  }
});
13 / Stories & Scenarios

Real workflows, and how to solve them

Every one of these is a real scenario that a Folio user has hit. Each one ends with a concrete solution.

The midnight landing page

You're in bed. Your friend just messaged about their business launch tomorrow and they don't have a landing page yet. You don't own a laptop — or it's dead.

What you do: Open Folio on your phone. New project → Landing template. Edit the headline and subheadline. Drop in the photo they sent. Deploy. Send them the URL. Total time: 4 minutes.

The train-based bug fix

You're on the train. No signal. You've been chasing a CSS bug for 2 days and it just clicked — one child in your grid is setting a minimum width that collapses everything else.

What you do: Open Folio (offline). Find the CSS file. Fix the min-width property. Commit — saved locally. When you arrive home and WiFi reconnects, the change syncs. Deploy from your phone. Done.

The portfolio deploy

You built a portfolio project for a job application. It's live but the "About" page still says "Coming soon." The interviewer said they'd look at it tonight.

What you do: Edit about.html. Commit. Redeploy. The URL never changes — the interviewer sees the updated version on next refresh. Total time: 90 seconds.

The collaborator

Your friend is a designer. They want to fix the colors on your side project. You don't want them touching your JS.

What you do: Sharing tab → invite them as Editor. They accept. They open the CSS file and change a color. You get a push notification. You check the Versions tab and see the diff. Everything's fine. You tap Deploy.

The rollback in seconds

You deployed and now the site is broken. It worked yesterday, but you've made 12 commits since.

What you do: Open the Deploys tab. Find yesterday's deployment. Tap Redeploy. The live site is on yesterday's code in ~2 seconds. Now you have time to actually debug what broke.

The wrong-click delete

You deleted the wrong file. There's no trash bin — Folio's deletes are permanent.

What you do: Open the Commits tab. Find the most recent commit from before the delete. Tap Restore. The whole project reverts to that snapshot. The file is back. Your last 20 minutes of unrelated changes are gone, but you learned to commit more often.

Better next time: Commit before destructive operations. Even a 30-second-old commit is enough.

The guestbook

You want a small "say hi" section on your site. Visitors type their name and a message. You want to display the last 20 messages. You don't want a backend.

What you do: Enable the JSON database in Sharing. Add a form and a script that POSTs each message under messages/msg_{timestamp}. Add a reader that GETs the DB and renders the messages. Copy-paste the code from the Recipes chapter. Live in 10 minutes.

The analytics curiosity

You deployed a link to a Slack group with 300 people. Did anyone actually click? Is it getting traffic?

What you do: Open the project Overview. There's a "today" stat that updates live. You see the spike in the sparkline. Then you open the Analytics tab and see which page got the most views and where they came from.

The "why is my JSON DB empty"

You deployed a project that reads from db/get. The console shows the response but data is an empty object {}.

Why: The DB exists but nothing's been written to it yet. Public reads succeed — they just return {} because that's what's in it.

Fix: Write to it once from the Data tab, or from the recipe in Chapter 12.

The "my writes stopped working"

You've been testing your app and after 20 writes, the API returns a 429 error.

Why: The rate limit is 100 writes per hour per project. You hit it.

Fix: Slow down testing. The response includes retryAfter in seconds — show it to the user and disable the button. In production, batch writes or use a server.

The "my database is full"

You've been saving images as data URLs to the JSON DB. The response is now 413.

Why: 15 MB DB limit. Images count toward it.

Fix: Store images as files in the project instead. Or move them to an external host and store only URLs in the DB.

The "I need a bigger project"

You built a full photo gallery. Each photo is 3 MB. After 4 photos, deploys fail.

Why: Total project size limit is 10 MB, 2 MB per file after upload. Images are stored as data URLs — 3 MB images become 4 MB data URLs.

Fix: Compress images before uploading. Or host on a CDN and reference by URL. Or split into multiple projects and link between them.

Suggestions to get better at Folio

Commit more than you think you need to

Commits are free. Commit before every edit, every deploy, every collaboration session. The worst case is you have a clean history to diff against.

Use Notes as your workbench

Before you start a big change, open a Note and write what you're about to do. When you're done, write what worked. When you come back in 3 weeks, you'll thank yourself.

Preview before every deploy

Fullscreen preview shows exactly what will ship. If it works in preview, it works live. If it doesn't — you saved yourself a rollback.

Store your API key somewhere else

Don't paste your project's fol_... key directly into client-side code. Even on a throwaway project. Treat it like a password — because that's what it is.

Set OG image on every project

It's one field in the Meta Tags card. It's the difference between a boring gray link and a beautiful preview card when you share your site.

15 / Analytics

See who's visiting what

Every deployed project tracks anonymous visits, page views, and API usage. It's private, aggregated, and never sold.

How tracking works

When your project is deployed and someone visits it, Folio's analytics script fires once. It sends the project ID, the page path, and the referring URL. Nothing else — no fingerprinting, no IP storage, no personal data.

What you see

The project's Overview tab shows today's visits, 7-day total, all-time total, top page, and a tiny sparkline chart.
