01 / Quick Start

Your first project in under a minute

Folio is designed to feel like an app — not a website. Everything works on a phone, everything is offline-ready, and there's no setup step between you and writing code.

Two surfaces, one project

Every Folio project has two working surfaces:

  • The Editor — / or /?pid=.... Where you write code, manage files, and preview.
  • The AI Cockpit — /ai?pid=.... Where you use the AI to explain, debug, document, plan, and review. Has a chat, sidebar with artifacts, and can apply patches with your approval.

Both share the same underlying files, versions, and deploy state. Switch between them any time.

Sign in vs. guest

Create & edit projects✓ Local only✓ Synced
Preview projects✓✓
AI tasks5 of 22All 22
Deploy to a live URL—✓
Collaborators—✓
Analytics—✓
JSON database—✓
Try it without signing up

You can use Folio as a guest forever. When you're ready to keep your work safe across devices, sign in from the profile icon.

Your first five minutes

  1. Tap New project, name it, choose the Landing template, tap Create.
  2. You're now in the editor with index.html open. Change the headline. Autosave fires in 2 seconds.
  3. Tap Preview to see it. If it works in preview, it works live.
  4. Tap Open in AI Cockpit. Ask the AI: "explain what main.js does".
  5. Ask: "add a dark mode toggle". The AI proposes a diff. Review it, click Accept. Undo is available for 10 seconds.
  6. Back in the editor, Deploy. You have a live URL in 3 seconds.
You never need to save manually

Folio auto-saves 2 seconds after you stop typing. The Ctrl + S shortcut exists if you want to force it, but you'll rarely need it.

03 / Files & Folders

Structured like a real project

Folio's file tree behaves like your laptop's — except it fits in your thumb.

The file tree

On the left (or behind the menu button on mobile) sits the Files panel. Tap a folder to expand it, tap a file to open it.

Creating files with paths

Type src/app.js and Folio creates a src folder and puts app.js inside. Nested paths work too: src/components/Button.jsx creates three levels.

Renaming and deleting

Hover (or long-press on mobile) any file or folder to reveal Rename and Delete.

Deletes are permanent

There's no trash bin. Commit before you delete — that way you can restore from history.

Importing files

Tap Import to open your device's file picker. Text files are imported as-is. Images, PDFs, videos, and audio are stored as data URLs.

Project files vs. hidden files

Two files live in every project but don't appear in the tree:

  • notes.json — your notes
  • ai.json — AI threads, drafts, pending proposals

Both export with .folio backups. Both stay private when you deploy.

What happens under the hood

  1. Finds your HTML file — preferring index.html at the root.
  2. Inlines every linked CSS file into a <style> tag.
  3. Inlines every linked JS file into a <script> tag.

07 / Commits

Version history without git

Folio gives you the safety net of version control without the complexity of branches, remotes, or merge conflicts.

What a commit is

A commit is a snapshot of your entire project at a moment in time. Unlike git, Folio's commits are linear — no branches, no merge conflicts.

Making a commit

  1. Tap Commit in the editor toolbar.
  2. A modal opens showing all files changed since your last commit.
  3. Folio auto-generates a message — edit it or accept it.
  4. Tap Commit.

Let the AI draft your message

From the AI Cockpit, run the commitMsg task. The AI returns a subject line and body based on the actual diff. Click Use this message and the commit dialog opens prefilled.

Comparing commits

Tap Diff on any commit for a colour-coded comparison: green added, red removed, amber changed.

Restoring to an old commit

Tap Restore on any commit. Before restoring, Folio creates a snapshot of your current state — so even restoring is reversible.

10 / Deploy

Your project, on the internet

Deploy any project to a live URL with one tap. No build steps, no configuration, no CI.

What deploy does

  1. Collects every file in your project (except notes.json and ai.json).
  2. Applies your meta tags to the primary HTML file.
  3. Uploads everything to Folio's servers.
  4. Returns a live URL. Generates a thumbnail for the projects list.

Where the URL lives

Live URL format
text 
https://foliostudios.vercel.app/api/host
  ?action=serve
  &pid=YOUR_PROJECT_ID
  &path=index.html

Deploy limits

Each project can be deployed up to 10 times per hour. Deploying requires an account — guests can build and preview but not deploy.

Let the AI draft the deploy summary

From the AI Cockpit, run the writeDeploy host task. The AI returns a summary and changed-file list based on what's actually different since your last deploy. Click Open deploy and the confirmation opens prefilled.

Taking offline

Use Take offline to hide the site without deleting it. Files and history stay intact. Redeploy any time.

Redeploying old versions

Every deploy keeps a snapshot. The Deploys tab shows the last 5 with thumbnails. Click any to preview that exact state. If a recent deploy broke something, one tap redeploys the previous version.

11 / JSON Database

Read and write JSON from your deployed site

Every project has a private JSON blob attached — a key-value store you can read and write from your site.

Not a real database

No queries, no indexes, no per-user records. It's enough for guestbooks, configs, waitlists, and lightweight applications.

Enable public reads

By default, nobody can read the DB. To let visitors read it, go to Sharing → JSON database API → Public.

Reading from your site

read-db.js
javascript 
const res = await fetch(
  'https://foliostudios.vercel.app/api/host' +
  '?action=db/get&pid=YOUR_PID'
);
const { data } = await res.json();
console.log(data);

Writing — three modes

ModeBody shapeUse when
Path write{ key, value }Editing one field
Merge write{ data, mode: "merge" }Replacing a top-level subtree
Replace write{ data }Full DB replacement

Limits & security

15 MB total per project DB. Writes that exceed return 413.

100 writes per hour per project. The response includes rateLimit and space.

Writes are not transactional. Concurrent writes race silently.

If you embed the API key in client-side JS, anyone can read it in DevTools and write to your DB.

For anything beyond a toy, proxy writes through a small backend.

12 / Production Recipes

Real patterns for real apps

The JSON DB has no queries, no indexes, and no auth. Here's how to build production-grade patterns on top of those constraints.

Read this first

The patterns below are real, but they come with real trade-offs. The DB is a data store, not a database. Every pattern here exists because the platform doesn't have a real backend.

1. Authentication (token-based)

Store users as { users: { [username]: { salt, hash, createdAt } } }. Use Web Crypto PBKDF2 to hash passwords client-side. Sessions live in localStorage as signed tokens.

auth.js
javascript 
async function signup(username, password) {
  const salt = crypto.randomUUID();
  const hash = await hashPassword(password, salt);
  await fetch(API + '?action=db/set&pid=' + PID, {
    method: 'POST',
    headers: {
      'content-type': 'application/json',
      'x-project-key': KEY
    },
    body: JSON.stringify({
      pid: PID,
      key: 'users/' + username,
      value: { salt, hash, createdAt: Date.now() }
    })
  });
}
Auth is not secure without a backend

Anyone with the API key can read all users. This works for a "closed front door" (members-only links) but not for holding real user secrets. If you need real auth, add a proxy server.

2. Rate limiting

Store per-IP counts in { rateLimits: { [ip]: { bucket: { count, resetAt } } } }. Since the DB has no atomic increments, "check-then-write" is racy. The pattern below tolerates a small overshoot.

rate-limit.js
javascript 
async function rateLimit(ip, action, max, windowMs) {
  const now = Date.now();
  const res = await fetch(API + '?action=db/get&pid=' + PID);
  const { data } = await res.json();
  const bucket = data.rateLimits?.[ip]?.[action];

  if (!bucket || bucket.resetAt < now) {
    // Reset
    await dbSet('rateLimits/' + ip + '/' + action, {
      count: 1, resetAt: now + windowMs
    });
    return { allowed: true, remaining: max - 1 };
  }

  if (bucket.count >= max) {
    return { allowed: false, retryAt: bucket.resetAt };
  }

  await dbSet('rateLimits/' + ip + '/' + action, {
    count: bucket.count + 1, resetAt: bucket.resetAt
  });
  return { allowed: true, remaining: max - bucket.count - 1 };
}

Trade-off: under concurrency, two requests can both see count = max - 1 and both proceed. Tolerate a small overshoot or move rate limiting to a real backend.

3. CRUD posts

Store as { posts: { [id]: { title, body, authorUid, createdAt, published } } }. Use path writes for publish toggles, replace writes for full edits.

posts.js
javascript 
async function createPost(title, body, authorUid) {
  const id = 'p_' + Date.now();
  await dbSet('posts/' + id, {
    title, body, authorUid,
    createdAt: Date.now(),
    published: false
  });
  return id;
}

async function publishPost(id) {
  // Path write — only `published` changes
  await dbSet('posts/' + id + '/published', true);
}

async function listPosts() {
  const res = await fetch(API + '?action=db/get&pid=' + PID);
  const { data } = await res.json();
  return Object.entries(data.posts || {})
    .map(([id, post]) => ({ id, ...post }))
    .filter(p => p.published)
    .sort((a, b) => b.createdAt - a.createdAt);
}

4. File uploads (external)

The DB does not store binary data. Use an external image host and store only URLs. Cloudinary's unsigned upload is the simplest:

upload.js
javascript 
async function uploadImage(file) {
  const form = new FormData();
  form.append('file', file);
  form.append('upload_preset', 'YOUR_UNSIGNED_PRESET');
  const res = await fetch(
    'https://api.cloudinary.com/v1_1/YOUR_CLOUD_NAME/image/upload',
    { method: 'POST', body: form }
  );
  const { secure_url } = await res.json();
  return secure_url;
}

// Then store the URL in the DB

6. Real-time updates (polling)

The DB has no websockets. Poll every N seconds with exponential backoff on errors.

poll.js
javascript 
function startPolling(intervalMs, onUpdate) {
  let timer = null;
  let currentInterval = intervalMs;
  async function tick() {
    try {
      const res = await fetch(API + '?action=db/get&pid=' + PID);
      const { data } = await res.json();
      onUpdate(data);
      currentInterval = intervalMs;
    } catch (err) {
      currentInterval = Math.min(currentInterval * 2, 60000);
    }
    timer = setTimeout(tick, currentInterval);
  }
  tick();
  return () => clearTimeout(timer);
}

Every one of these platforms ports cleanly to Supabase, Firebase, or a custom Postgres. The schemas are the same. The write patterns are the same. When you outgrow the JSON DB, you migrate the storage layer and keep the app.

Guest vs. signed-in

Five tasks are available to guests: explain, logExplain, metatags, brainstorm, diagram. The other 17 require sign-in. The remaining 17 aren't shown at all if you're a guest.

The permission model

Every AI action is gated by a capability. Three states:

  • off — the AI cannot propose this action at all.
  • ask — the AI proposes; you approve each action.
  • auto — the AI acts immediately. You have 10 seconds to undo.

Capabilities: read.files, write.files, install.files, delete.files, read.db, write.db, run.preview, commit, deploy.

Never set deploy to auto

Every AI action that touches your live site should require your approval. Keep deploy at ask or off. Always.

Applying a diff

  1. AI returns a diff artifact.
  2. You see a side-by-side diff with Accept / Reject / Review.
  3. Click Review to open the full diff view.
  4. Click Accept to write the patch to IDB, then sync to server.
  5. An Undo toast appears for 10 seconds.

The context bar

Above the chat input sits a pinned context bar showing the files currently attached. It always shows the token count and warns when you're approaching the model's budget.

The ai.json file

Threads, drafts, and pending proposals live in ai.json — a hidden project file. It exports with .folio. It stays private when you deploy.

15 / AI Workflows

How to use the AI like a pro

The cockpit is powerful but it rewards specific workflows. These are the five that pay off most.

Workflow 1 — The review loop

The single most productive pattern. Five steps, all in one cockpit session:

  1. Ask. "Fix the loop bug in main.js."
  2. Review. The AI returns findings + a diff. Check the findings first — they tell you what the AI understood.
  3. Accept. Click Accept on the diff. Watch the editor reload with the fix.
  4. Commit. Run commitMsg. The commit dialog opens prefilled.
  5. Deploy. Run writeDeploy. The deploy confirmation opens prefilled.

This turns a 20-minute manual cycle into 2 minutes.

Workflow 2 — Plan → Scaffold → Audit

For new projects, don't start with the AI writing files. Start with the AI writing a plan.

  1. Ask brainstorm: "give me 5 directions for a todo app."
  2. Pick a concept. Feed its title into scaffold as the concept field.
  3. The scaffold returns a files artifact. Before accepting, run audit and struggle on those draft files.
  4. Fix any issues the audit finds. Then accept.

Workflow 3 — Read → Document → Ship

For an existing project you haven't touched in weeks:

  1. Run readProject to get an AI-generated summary of the current state.
  2. Run docs to generate a full README.
  3. Save the docs to notes (one tap).
  4. If everything looks right, run writeDeploy and ship.

Workflow 4 — Debug with context

When something's broken and you're not sure why:

  1. Open the file with the suspected bug in the editor.
  2. Open the cockpit. The context bar shows the file attached.
  3. Run debug.
  4. Read the findings. They tell you exactly which line.
  5. Accept the diff. Run the preview. Check the console.

Workflow 5 — The permission hygiene audit

Once a week, check your permission states:

  • deploy should be ask or off. Never auto.
  • delete.files should be off unless you're in a sandbox.
  • write.db should be ask unless you're running a batch migration.
  • auto should only be enabled for read.* capabilities.
Every AI action is reversible

Diff accept has a 10-second undo. File creation has a 10-second undo. DB write has a 10-second undo. Commit is not undoable but can be restored from Versions. Deploy is not undoable but can be redeployed from Deploys.

Recipe 2 — A working todo list

app.js
javascript 
const form = document.getElementById('new-todo');
const input = document.getElementById('todo-input');
const list = document.getElementById('todo-list');

function addTodo(text) {
  const li = document.createElement('li');
  const cb = document.createElement('input');
  cb.type = 'checkbox';
  cb.addEventListener('change', () => {
    li.style.opacity = cb.checked ? '0.5' : '1';
    li.style.textDecoration = cb.checked ? 'line-through' : 'none';
  });
  const span = document.createElement('span');
  span.textContent = text;
  const del = document.createElement('button');
  del.textContent = '×';
  del.addEventListener('click', () => li.remove());
  li.append(cb, span, del);
  list.appendChild(li);
}

form.addEventListener('submit', (e) => {
  e.preventDefault();
  const text = input.value.trim();
  if (!text) return;
  addTodo(text);
  input.value = '';
  input.focus();
});
17 / Stories & Scenarios

Real workflows, and how to solve them

Every one of these is a real scenario a Folio user has hit. Each ends with a concrete solution.

The midnight landing page

Your friend launches tomorrow. No landing page. You don't own a laptop.

You: New project → Landing template. Edit headline. Deploy. 4 minutes.

The AI reviews your bug fix

You think you fixed a bug, but you're not sure. You're on the train, WiFi off.

You: In the cockpit, attach main.js. Run debug. AI returns findings + diff. You accept the fix. When WiFi returns, it syncs and deploys.

The scaffold that gets audited

You asked the AI to scaffold a blog. It looks fine. You deploy. Two days later you realize it uses innerHTML unsafely.

Better: Before accepting a scaffold, run audit on the draft files. The audit catches innerHTML, missing alt text, eval, and more. Fix those before accepting.

The rollback in seconds

You deployed and now the site is broken. It worked yesterday, but you've made 12 commits since.

You: Open the Deploys tab. Find yesterday's deployment. Tap Redeploy. Live site is on yesterday's code in ~2 seconds.

The wrong-click delete

You deleted the wrong file. Folio has no trash bin.

You: Commits tab. Find the last commit before the delete. Restore. The file is back. Your last 20 minutes of changes are lost, but you learned to commit more.

The production guestbook

You want a guestbook on your site. Visitors submit, you approve, they appear. You don't want a backend.

You: Deploy the guestbook pattern from chapter 13. JSON DB holds the messages. Admin panel at /admin?token=xxx. Rate limiting from chapter 12. Ships in 2 hours.

The "why is my JSON DB empty"

You deployed a site reading from db/get. Console shows the response but data is {}.

Why: The DB exists but nothing's been written yet. Public reads succeed — they return what's there.

Fix: Write once from the Data tab, or run the seed recipe from chapter 12.

The "my writes stopped working"

After 20 test writes, the API returns a 429.

Why: 100 writes per hour per project. You hit it.

Fix: Slow down. Show retryAfter to the user. In production, batch writes or move to a backend.

Suggestions to get better

Commit before every destructive action

Even a 30-second-old commit is enough. Restore from Commits. Deletes are permanent — but commits are forever.

Audit before accepting scaffolds

The AI scaffolds fast but doesn't audit itself. Run audit and struggle on every scaffold draft before accepting. It takes 20 seconds and catches 80% of the issues.

Never set deploy permission to auto

Every AI action that touches your live site should require your approval. Always.
