Documentation

How Folio works

Everything you need to know about using the editor, hosting projects, and integrating the JSON database.

1 Getting started

Create your first project

Open foliostudios.vercel.app and tap New project. Give it a name, choose an icon, and you'll land in the editor with three starter files: index.html, style.css, and app.js.

The three core panels

  • Editor — write code with syntax highlighting, autocomplete, and search.
  • Files — create, rename, and organize files and folders. Everything lives in your browser first.
  • Preview — see your HTML render live. Full-screen, mini panel, or open in a new tab.

Saving

Every keystroke autosaves to your local browser storage after 2 seconds. Files are marked dirty until saved. The save icon in the toolbar forces an immediate save, and Ctrl/Cmd + S works too.

2 Editing code

Supported languages

Syntax highlighting is built in for HTML, CSS, JavaScript, TypeScript, JSX/TSX, JSON, Markdown, Python, and several other common formats.

Toolbar actions

  • Undo / Redo — standard behavior, scoped per file.
  • Find — search in the current file. Ctrl/Cmd + F.
  • Format — auto-format HTML, CSS, JS, JSON, or Markdown using Prettier.
  • Symbols — quick-insert common characters ({, ;, <, etc.).

Versions

Tap Commit in the toolbar to snapshot your project. Every commit is versioned and you can restore or diff any previous version later. Versions live in your local browser storage until you sync to the cloud.

3 Deploying a project

Before you deploy

You need a Folio account. If you're not signed in, the app works fully as a guest — everything is stored locally and survives browser refreshes. But deploying requires a session.

How deployment works

Click Host in the toolbar or open the Deploys tab in your project. Folio packages every file in the project (up to 8 MB total) and serves them from the Folio origin. You get a live URL of the form:

https://foliostudios.vercel.app/api/host
  ?action=serve
  &pid=YOUR_PROJECT_ID
  &path=index.html

How files are served

Every file in the project — HTML, CSS, JS, images — is served through the action=serve endpoint. When the browser loads your index.html, Folio rewrites every relative URL in the page (like <link href="style.css">) to point through the same endpoint. So your multi-file project just works, with no config.

Taking a project offline

From the Deploys tab, tap Take offline. The URL stops serving immediately, but your files and versions stay intact. Re-deploy any time to bring it back.

4 The JSON database

What it is

Every project has a private JSON blob attached to it — a key-value store you can read and write from your deployed site. It's not a real database (no queries, no indexes, no per-user records), but it's enough for guestbooks, site config, todo lists, feature flags, and small dynamic content.

Enable public reads

By default, nobody can read the DB. To let visitors read it, go to your project page → Sharing → flip JSON database API to Public.

Reading

const res = await fetch(
  'https://foliostudios.vercel.app/api/host' +
  '?action=db/get&pid=YOUR_PID'
);
const { data } = await res.json();
console.log(data);

No auth needed if the DB is public. If you want to read it privately, send the project's API key in an x-project-key header.

Writing — three modes

Writes always require the API key. Generate one at project page → Sharing → API key. It's shown once — copy it and keep it safe.

There are three ways to write, and you choose by the shape of your request body:

1. Path write (recommended for edits)

Send a key (slash-separated path) and a value. Only that path is touched — every sibling is preserved. This is the safest way to update a single field.

// Set posts/p_abc/heart to 42, leaving every other post intact
await fetch(
  'https://foliostudios.vercel.app/api/host' +
  '?action=db/set&pid=YOUR_PID',
  {
    method: 'POST',
    headers: {
      'content-type': 'application/json',
      'x-project-key': 'fol_...'
    },
    body: JSON.stringify({
      pid: 'YOUR_PID',
      key: 'posts/p_abc/heart',
      value: 42
    })
  }
);

Pass value: null to delete a single field or array entry without touching its siblings.

2. Merge write (partial top-level update)

Send a data object with mode: "merge". Each top-level key you send replaces that subtree — the rest of the DB is untouched. Because it's a top-level replacement, you must send the full subtree for any key you include.

// Replace config wholesale; leave posts and members alone
await fetch(
  'https://foliostudios.vercel.app/api/host' +
  '?action=db/set&pid=YOUR_PID',
  {
    method: 'POST',
    headers: {
      'content-type': 'application/json',
      'x-project-key': 'fol_...'
    },
    body: JSON.stringify({
      pid: 'YOUR_PID',
      data: {
        config: {
          theme: 'dark',
          welcome: 'No posts yet — say hi.'
        }
      },
      mode: 'merge'
    })
  }
);

Warning: this is not a deep merge. If you send { posts: { p_abc: {...} } } with merge mode, the entire posts object becomes { p_abc: {...} } — every other post is dropped. To update one post without wiping others, either use a path write (mode 1) or send the full posts object in the merge.

3. Replace write (full DB replacement)

Send a data object with no mode. This replaces the entire projectData/{pid} node — everything not present in your payload is deleted.

// Wipe the DB and set it to a fresh object
await fetch(
  'https://foliostudios.vercel.app/api/host' +
  '?action=db/set&pid=YOUR_PID',
  {
    method: 'POST',
    headers: {
      'content-type': 'application/json',
      'x-project-key': 'fol_...'
    },
    body: JSON.stringify({
      pid: 'YOUR_PID',
      data: {
        config: { theme: 'dark' },
        posts: {},
        members: {}
      }
    })
  }
);

Use this only when you genuinely want to overwrite everything — e.g. importing a backup, resetting a project, or replacing the DB in one atomic call. For incremental changes, use mode 1 or 2.

Which mode should I use?

  • Editing one field (a reaction, a vote, a rename) → path write (key + value).
  • Updating a whole top-level object (config, members, posts) → merge write (data + mode: "merge"), sending the complete subtree.
  • Resetting / importing / atomic replace → replace write (data, no mode).

Limits

  • 15 MB total per project DB. Writes that push the DB over the limit return 413.
  • 100 writes per hour per project via dbSet. The response includes rateLimit and space so you can back off gracefully.
  • Writes are not transactional. If you send a replace write while another client is mid-merge, one wins silently.

Security note

If you embed the key in client-side JavaScript, anyone who opens DevTools can read it and write to your DB. For anything beyond a toy project, put the key in a small backend and proxy writes through it.

5 Sharing and access

Visibility axes

Each project has five independent public/private toggles in the Sharing tab:

  • Show in profile — project appears on your public profile page.
  • Live site link — the "Visit live site" button shows on the share page.
  • Code viewer — visitors can browse your source files.
  • Language breakdown — show the language percentage badges.
  • JSON database API — external reads via db/get are allowed.

Inviting collaborators

From the Sharing tab, tap Invite. Enter their Folio username and choose a role:

  • Viewer — can open the project and see files.
  • Commenter — viewer, plus can leave comments.
  • Editor — full write access, including deploys.

They'll get a notification with a link. The invite expires in 7 days.

6 Exporting your work

Backup formats

From the Downloads tab:

  • .folio — full backup including files, versions, JSON DB, and schema. Re-importable through the same tab.
  • .zip — just the current files, ready to open in any local editor.
  • .json — the JSON DB alone.

Importing a backup

From the same tab, tap Import .folio and select a backup file. Files merge into the current project — existing files are overwritten by the backup's versions.

Getting your work out

Your files always live in your browser first, so even if Folio vanished tomorrow, your work would still be in your IndexedDB. But it's still worth exporting regular backups — browsers occasionally wipe local storage during "clear site data" operations.
