Building

Files & assets

Everything you write in the editor becomes a file. Everything you upload becomes a file too — but with a few quiet rules.

Creating files

Three ways to add a file:

  • Sidebar → files panel → + button — prompts for a path.
  • Toolbar → More → New — same prompt.
  • Import — pick one or more local files. Binary assets (images, PDFs, fonts, audio, video) are automatically uploaded to a CDN and stored as HTTPS URLs.

Paths support nesting with /: src/components/button.js. Folders are implicit — they exist because a file lives under that prefix.

File size limits

LimitValue
Max size per file4 MB
Max total per project10 MB (default; can be raised)
Max path length500 characters
Max path segment100 characters

Files over the limit are rejected before upload. The editor shows a clear error and skips that file — other files in the same batch still upload.

Binary assets

When you import a binary file, Folio uploads it to the image host and stores the resulting HTTPS URL as the file's content. When the site is served, the browser receives a redirect (302) to the CDN — not a base64 blob. This keeps the database small and pages fast.

The following extensions trigger binary handling:

  • Images — png, jpg, jpeg, gif, webp, svg, bmp, ico, avif
  • Documents — pdf
  • Fonts — woff, woff2, ttf, otf
  • Media — mp4, webm, mp3, wav, ogg

Reserved paths

PathWhat it does
api/*.jsPrivate API routes — executed but not served as files
notes.jsonManaged by the Notes tab, treated as a system file
.gitkeep / .keepPlaceholders — skipped on deploy
Don't put secrets in files

Files are served publicly. API keys belong in Secrets, not in config.js.

Deleting files

Hover a file in the sidebar to see the trash icon. Deleting removes the file from IndexedDB and, if you're online, from the server. Deleted files are not recoverable unless you committed a version beforehand — so commit before destructive edits.

Preview

See what you're building without leaving the editor. Three preview modes for three workflows.

Three modes

ModeBest for
FullscreenChecking layouts on the real viewport. Comes with a console underneath.
New tabTesting on a second monitor, or debugging with full browser devtools.
Mini panelWatching changes as you type. Floats in the corner.

The caret next to the Preview button in the header opens a mode picker. Your choice persists across sessions.

What preview does

The preview assembles a live page from your files, in memory. It:

  • Inlines CSS — <link href="style.css"> becomes inline <style>.
  • Inlines images — <img src="logo.png"> uses the stored data URI or CDN URL.
  • Bridges console — console.log from the iframe flows to the preview console.
  • Injects meta tags — your title, description, and OG image are inserted automatically.
Preview is not deployment

Preview runs entirely in your browser. API calls in preview hit Folio's live API; if you haven't deployed with the current secrets, you may see errors. Deploy to see the real thing.

Previewing a specific file

When you have more than one HTML file, a dropdown appears in the preview toolbar. Choose any file to preview it. Default is index.html.

Versions & commits

Snapshots of your whole project. Restore in one click, diff any two versions.

Making a commit

  1. Save the files you want in the snapshot (or accept they won't be included).
  2. Click Commit in the toolbar, or Commit version in the Versions tab.
  3. The dialog shows changed files with +/- line estimates, plus an auto-generated message. Edit it if you want.
  4. Tap Commit. Done.

Auto-message format: edit: index.html (+12, −3) for a single-file change, edit: 3 files (+40, −8) for multiple. It's meant to be readable, not perfect.

Offline commits

Commit with no internet? The commit saves to IndexedDB immediately and queues a server sync. When you reconnect:

  • The queue auto-flushes every 30 seconds while online.
  • Failed syncs retry up to 5 times, then drop with a warning.
  • The sync badge on the notification bell shows pending count.

Restoring a version

Open the Versions tab in the sidebar. Each commit shows restore and delete. Restoring:

  1. Auto-commits the current state first (so you can undo the undo).
  2. Replaces all files with the version's snapshot.
  3. If the version was a deploy, the live site stays on the current deployment until you redeploy.
Restore replaces, it doesn't merge

Any uncommitted files not in the version will be deleted. Commit first if you're unsure.

Shipping

Deploying

One tap to a live URL. Here's what happens under the hood.

What a deploy does

  1. Upload files — all regular files go to the file store.
  2. Upload api/*.js — validated and stored separately.
  3. Create a version snapshot — full state, immutable.
  4. Write a deployment record — URL, timestamp, version reference.
  5. Create or repoint the short link — auto-created on first deploy.
  6. Generate OG image + thumbnail — for share cards.

Progress card

During deploy, a persistent progress card appears in the top-right corner (top-center on mobile). It shows:

  • Stage text — Preparing → Uploading → Activating → Live
  • Percentage — 0% → 100%
  • Elapsed time — a running counter

You can keep editing, switch tabs, open panels, or navigate around the editor while it's running. When it's done, the card flashes green and disappears.

Don't close the tab

Leaving the page mid-deploy triggers a confirmation dialog. You can stay or leave — the deploy continues server-side either way, but you won't see the result bar if you leave.

Result bar

When deploy succeeds, a persistent bar appears at the bottom of the editor. It contains:

  • The live URL on foliosites.vercel.app.
  • The short link on folio.xo.je (if one exists).
  • A copy button next to each — tap to copy.
  • A close button — the bar stays until you dismiss it.

Deployment history

The last 5 deployments are kept. Each has:

  • A preview URL — append ?from={deploymentId} to see that specific version.
  • The deployment's version snapshot — can be restored or redeployed.
  • The state — READY or OFFLINE.

Older deployments drop off the list. To keep a version permanently, commit it first — commits aren't pruned.

Taking a site offline

Owners can take a live site offline. The URL stops working immediately; the last live URL is preserved. Redeploying brings it back. This is different from deleting — the files and deployments stay.

Deploy permissions

Only owners and editors can deploy. Viewers and commenters can see files and history but not publish. Rate limit: 10 deploys per hour per project.

Shipping

Short links

A custom URL on folio.xo.je that redirects to your live site. Auto-created. Fully customisable.

Auto-creation

On first deploy, a short link is created from your project slug. Deploys after that repoint the existing key — same URL, new destination.

Claiming a custom name

  1. Open Settings → Short link in the project dashboard.
  2. Enter a name — 3-30 lowercase letters/digits, must start with a letter.
  3. Tap Claim.
  4. If taken, pick from 3 suggested variants or try another name.

Copying from the editor

The link icon in the editor header:

  • Green tinted — a short link exists; click to copy.
  • Grey — no short link yet; click to open the project page's short link settings.

The copy button pulses green on success, then returns to normal.

Releasing a name

Settings → Short link → Release. Confirmation dialog first. After releasing, the short link 404s immediately. Another project can claim it.

Released links 404 immediately

If the link is printed on a business card, don't release it. Change the destination instead by deploying a different project to it.

Reserved names

Blocked: api, www, admin, login, register, settings, dashboard, help, docs, and similar. Also any name starting with a digit or containing uppercase, spaces, or punctuation.

Visibility

Five independent switches. Together they decide what the public sees.

The five axes

AxisPublic means
ProfileProject appears on your public profile page at /{username}
Live siteVisitors can open the deployed site
CodeVisitors can browse the source files from the share page
LanguagesLanguage breakdown (HTML 40%, CSS 30%…) is visible
DBExternal clients can read your JSON database without auth

Everything defaults to private. Flipping any axis to public makes that specific thing visible; nothing else changes.

When is a project accessible?

  • Owner/editor — always, regardless of visibility.
  • Collaborator (viewer/commenter) — if they've been invited to that project.
  • Public visitor — only if the relevant axis is public.

Revoking access

Toggle an axis back to private and it becomes inaccessible immediately on the next request. Cached responses may serve stale content for up to 60 seconds — no more.

Public DB means public DB

Flipping the DB axis to public lets anyone read your JSON database. Not just your API — anyone with the project ID. Enable only if the data is genuinely public.

Collaborators

Owners invite collaborators by username from Settings. Four roles:

RoleCan do
ViewerSee files and versions
CommenterEverything a viewer can, plus comments
EditorEdit files, commit, deploy
OwnerEverything, plus delete the project
Backend

Secrets

Encrypted environment variables per project. Available to your API. Never to the browser (unless you ask).

Creating a secret

  1. Open the Secrets tab in the project dashboard.
  2. Tap New.
  3. Enter a key in UPPER_SNAKE_CASE — e.g. OPENAI_API_KEY.
  4. Enter the value.
  5. Choose visibility — private (default) or public.
  6. Tap Create.

Accessing secrets

From api/*.js:

const key = ENV.OPENAI_API_KEY;
const response = await fetch("https://api.openai.com/v1/chat/completions", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "Authorization": "Bearer " + key,
  },
  body: JSON.stringify({ model: "gpt-4o-mini", messages: [{ role: "user", content: "Hello" }] }),
});
return await response.json();

Private vs. public

VisibilityAppears inUse for
PrivateENV only (server)API keys, database passwords, anything secret
PublicENV + window.__SECRETS__ (when injection on)Publishable keys, anon Supabase, Stripe publishable

Frontend injection

Injection is an additional switch on the Secrets tab. When enabled, public secrets appear as window.__SECRETS__ in every served HTML response. Anyone viewing source can read them.

Access from frontend JS:

const stripe = window.__SECRETS__?.STRIPE_PUBLISHABLE_KEY;
const supabase = window.__SECRETS__?.SUPABASE_ANON_KEY;
Never mark a secret public by mistake

Public + injected = readable by anyone. OpenAI keys, Stripe secret keys, service role keys, database passwords — all should stay private.

Limits

LimitValue
Value size16 KB
Total per project512 KB
Count50
EncryptionAES-256-GCM (when FOLIO_SECRETS_KEY is set server-side)

Reserved names

Folio auto-injects these into ENV. You can't create secrets with these names:

  • PROJECT_ID, PROJECT_NAME, PROJECT_SLUG, PROJECT_URL
  • OWNER_USERNAME, OWNER_UID
  • DEPLOYMENT_ID, DEPLOYMENT_URL
  • FOLIO_BASE_URL, FOLIO_API_URL
  • API_ROUTE, REQUEST_ID, FOLIO_API_KEY
Backend

JSON database

A 15 MB key/value store per project. Firebase-backed. Read and write it from your API or your editor.

Data model

It's a JSON tree. No collections, no schema, no migrations — just nested objects and primitives. Arrays are stored as {"0":…,"1":…} because Firebase doesn't support them natively.

{
  "users": {
    "u_abc": { "name": "Alice", "joined": 1717000000 }
  },
  "counters": { "visits": 42 },
  "todos": {
    "t1": { "text": "Buy milk", "done": false }
  }
}

Reading from your API 

const BASE = ENV.FOLIO_BASE_URL;
const res = await fetch(BASE + "/api/host?action=db/get&pid=" + ENV.PROJECT_ID);
const { data } = await res.json();

const users = data.users || {};
const counters = data.counters || {};

This returns the whole tree. Read what you need, ignore the rest. The runtime intercepts this call — no network round trip.

Writing

Write one path at a time:

await fetch(BASE + "/api/host?action=db/set", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    pid: ENV.PROJECT_ID,
    key: "todos/t1",
    value: { text: "Buy milk", done: true },
  }),
});

Write many paths atomically:

await fetch(BASE + "/api/host?action=db/batch", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    pid: ENV.PROJECT_ID,
    updates: [
      { key: "todos/t1/done", value: true },
      { key: "counters/visits", value: 43 },
    ],
  }),
});

Deleting

Writing null deletes a path:

await fetch(BASE + "/api/host?action=db/set", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    pid: ENV.PROJECT_ID,
    key: "todos/t1",
    value: null,
  }),
});

Atomic increment 

await fetch(BASE + "/api/host?action=db/increment", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ pid: ENV.PROJECT_ID, key: "counters/visits", by: 1 }),
});

Compare-and-swap

Optimistic locking — only writes if the current value matches what you expected:

const res = await fetch(BASE + "/api/host?action=db/cas", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    pid: ENV.PROJECT_ID,
    key: "todos/t1",
    expected: { text: "Buy milk", done: false },
    value: { text: "Buy milk", done: true },
  }),
});
if (res.status === 409) {
  // Someone else edited first — read fresh and retry
  const current = (await res.json()).current;
}

The Data tab

The Data tab in the project dashboard is a visual editor for the JSON DB. It offers:

  • Tree view — expand/collapse, edit values inline (double-click), copy paths.
  • Raw view — edit the whole tree as JSON, with syntax highlighting.
  • Schema view — optional metadata to describe fields.
  • Auto-save — each change queues a write (debounced 800ms).
Reads are free, writes are limited

You can read the DB as often as you want. Writes are limited to 300 per minute per project. The Data tab batches rapid edits so you don't hit the limit.

Backend

Private API

Files under api/ become server routes. Your code runs in an isolated Chromium sandbox and can call allowed external hosts.

How it works

  • Every api/*.js file becomes a POST route.
  • Your code runs inside a headless Chromium page.
  • ENV, REQ, and FILES are available as globals.
  • Whatever the script returns is the response body.
  • The browser never sees your source code or secrets.

Your first route

Create api/hello.js:

return { message: "Hello from the server!" };

Deploy. Then call it:

const res = await fetch("/{username}/project/{slug}/api/hello", {
  method: "POST",
});
const { message } = await res.json();
// → { message: "Hello from the server!" }

The REQ object

FieldTypeDescription
REQ.methodstringHTTP method (usually POST)
REQ.headersobjectForwarded headers (Content-Type, Authorization, User-Agent, etc.)
REQ.bodyobjectParsed JSON request body
REQ.pidstringYour project ID
REQ.routestringThe route name (e.g. hello)
REQ.deploymentIdstringCurrent deployment ID
REQ.startTimenumberRequest start timestamp (ms)

Returning responses

ReturnResponse
{ hello: "world" }200, application/json
"Hello"200, text/plain
{ __status: 404, error: "Not found" }404, application/json
{ __contentType: "text/html", __body: "<h1>Hi</h1>" }200, text/html
throw new Error("boom")500, error
Always return something

If your script falls through without returning, the response is the string "null". Wrap in try/catch with a fallback return.

_system.js

Auto-created on first deploy. Provides 6 free routes:

RouteReturns
/api/health{ status, pid, deployed, responseMs }
/api/whoami{ pid, name, deployedAt, apiVersion }
/api/files{ files, count, totalBytes }
/api/statusRicher health
/api/version{ deploymentId, deployedAt, url }
/api/robotsrobots.txt as text/plain

api/ file rules

  • Flat folder — no subfolders inside api/
  • Lowercase filenames, .js only
  • No _ prefix except _system.js
  • Reserved: index.js, run.js, health.js, whoami.js, files.js, status.js, version.js, robots.js
  • Max 10 files, 50 KB each, 200 KB total

Sandbox restrictions

Your script runs in Chromium at about:blank — a non-secure context. These are unavailable:

  • crypto.subtle — use pure-JS SHA-256 instead
  • crypto.randomUUID — use crypto.getRandomValues
  • Relative fetch URLs — always build from ENV.FOLIO_BASE_URL
  • ES module imports from local files

External hosts

Your API can call external services. Which ones depends on how you reference them.

Four tiers

TierExamplesHow it's allowed
Built-in api.openai.com, api.stripe.com, api.supabase.co, api.github.com Always allowed — no config
Trusted images picsum.photos, images.unsplash.com, upload.wikimedia.org Always allowed
CDN imports cdn.jsdelivr.net, esm.sh, unpkg.com Always allowed
Per-project Any other host Must be declared (see below)

Declaring a host

Literal URL — auto-detected

If your code contains https://host.example/api anywhere, deploy scans it and adds the host. No config needed:

const res = await fetch("https://api.weather.com/v1/today");
// "api.weather.com" is added automatically on deploy

@allow comment — for dynamic hosts

If the host is built from a variable, declare it explicitly:

// @allow api.weather.com
// @allow api.example.com

const host = REQ.body.host || "api.weather.com";
const res = await fetch("https://" + host + "/v1/today");

Dashboard

Add a host from Settings → API tab → Allowed hosts. The backend validates DNS + HTTPS before storing.

What gets rejected

  • IP addresses (10.0.0.1, 169.254.169.254)
  • Hosts resolving to private IPs
  • localhost
  • *.vercel.app (Folio's own infrastructure)
  • Wildcards, ports, non-HTTPS
  • Hosts that don't respond to an HTTPS HEAD
Fetch fails? Check the logs.

If fetch returns TypeError: Failed to fetch, the host is blocked. Look for run.host_blocked in the API logs to see which host.

Offline & sync

Folio works offline. Here's exactly what works and what doesn't.

What works offline

  • Open any cached project
  • View files
  • Edit files
  • Save files
  • Commit versions (queued)
  • Search across files
  • Preview
  • Read your notes
  • View analytics (last cached)

What needs internet

  • Deploy
  • Pulling files from server (first visit on a new device)
  • Creating a new server project
  • Claiming or releasing short links
  • Editing secrets or database
  • API calls from the browser

How sync works

The sync system has two layers:

  1. Files — saved to IndexedDB immediately. Synced to the server on save (if online), or queued (if offline).
  2. Commits — always saved to IndexedDB. Server sync is best-effort: queued when offline, retried up to 5 times.

The sync queue

Offline changes live in a queue. Every 30 seconds, while online, the queue flushes:

  • Successful → removed from the queue.
  • Transient failure (network, server) → stays, retried up to 5 times.
  • Permanent failure (400, 403, 404) → dropped with a warning.

The sync badge on the notification bell shows the pending count. Zero means everything's on the server.

Conflict handling

Files use last-write-wins. If two people edit the same file, the last save wins. If you need safer concurrent editing, use the DB's compare-and-swap operation from the API — but files themselves don't have CAS.

Logs & errors

Where to look when something goes wrong.

API logs

The API tab in the project dashboard shows the last 50 API calls, filterable by route, status, and identity:

  • route — which API file
  • status — HTTP response code
  • durationMs — total wall time
  • via — anon, session, or api-key
  • fetchHosts — external hosts the script hit
  • errorClass — timeout, rate_limit, network, etc.

Event log

Every project action (deploy, commit, secret change, invite, DB write) is logged in Insights → Logs. Last 200 events kept.

Common errors

SymptomCauseFix
TypeError: Failed to fetch in API Blocked external host Add @allow host or a literal URL, redeploy

504 timeout API took too long Batch DB calls, reduce fetches — 7s cap on user code

Security

What Folio protects, and what's on you.

What Folio handles

  • Passwords — scrypt-hashed with random salt (N=16384, r=8, p=1). Never stored in plaintext.
  • Sessions — JWT with 30-day expiry, signed with server-side secret.
  • Secrets — AES-256-GCM encryption (when FOLIO_SECRETS_KEY is set).
  • Secrets isolation — private secrets never enter the browser. Public secrets are opt-in and clearly marked.
  • CORS — allowlist-driven. Only origins in domains.json can call the API.
  • Rate limiting — every sensitive action has a per-project or per-IP limit.
  • Sandbox — API scripts run in Chromium, not on your server.

What's your responsibility

  • Don't hardcode secrets in files. Use the Secrets tab.
  • Don't mark secrets public unless they're publishable. Publishable = safe to appear in browser source.
  • Validate input in your API. The runtime doesn't validate REQ.body.
  • Sanitize before returning HTML if you're using __contentType: "text/html". Folio doesn't escape for you.
  • Use HTTPS for external hosts. Non-HTTPS hosts are rejected at deploy.
  • Keep dependencies current. If you import from a CDN, pin versions explicitly.

API keys

Generate an API key from Settings → API key to call Folio's API from outside the browser. The key is shown once. It's also stored as ENV.FOLIO_API_KEY in your project secrets for use inside api/*.js.

Treat API keys like passwords

Anyone with your API key can act as your project. If it leaks, regenerate it immediately from Settings.
